# Decisions

## 2026-11-08 Database: SQLite through SQLAlchemy

- **Decision:** SQLite, accessed through SQLAlchemy.
- **Why:** Zero cost, one file, no extra service for peer reviewers to run. Data volume is small (scenarios and
  audit entries). SQLAlchemy keeps a later move to Postgres cheap.
- **Alternatives:** Postgres in docker-compose (more setup, a second container). Managed Postgres such as
  Cloud SQL or Supabase (cost and account setup).

## 2026-11-08 Auth: demo logins with signed JWT roles

- **Decision:** FastAPI issues a signed JWT for a demo Analyst or Reviewer login. The role is in the token and
  checked on each endpoint. Demo logins hold no real credentials.
- **Why:** Enough to show the approval workflow, no external service, works offline in docker-compose.
- **Alternatives:** Supabase Auth (outside the stack, needs an account). Session cookies (more state to manage).

## 2026-11-08 Gate 3: pricing-service gaps filled by a change request

- **Decision:** Ask the pricing service for a metadata endpoint, histogram counts and projected A/E. The backend
  only translates. See `_docs/contract-check.md`.
- **Why:** Keeps monitoring and rating-adjacent logic out of this repo.
- **Alternatives:** Backend derives them (breaks the no-rating-logic rule). Drop the UI fields (loses plan
  features).

## 2026-11-08 Hosting: always-free e2-micro VM with docker-compose (portable)

- **Decision:** One always-free GCP e2-micro VM in a free-tier US region (us-west1, us-central1 or us-east1),
  running docker-compose with three services: Caddy (static SPA build, reverse proxy of `/api`, automatic HTTPS
  on a free sslip.io hostname), the backend (SQLite on a mounted volume on the VM's persistent disk), and the
  published pricing-service image, reachable on the compose network only. A 1 GB swap file is added. Budget
  alert at £1.
- **Portability rules:** all config through environment variables. The frontend calls relative `/api` paths.
  Schema changes only through Alembic migrations. Everything VM-specific lives in `deploy/`.
- **Why:** Lowest cost, SQLite data persists across restarts, and the same compose file runs locally and for peer
  reviewers. Measured pricing service memory is about 70 MiB, so 1 GB plus swap should fit.
- **Costs (checked 8 Nov 2026):** VM and 30 GB standard disk are free. Not free: the external IPv4 address,
  about $0.005 per hour (about $3.65 a month, about $7.30 for two months). Egress beyond 1 GB a month (small
  for a demo). Prices from secondary sources, to be confirmed on the billing page when the VM is created.
- **Alternatives:** Cloud Run with a sidecar and reseeded SQLite (cheaper in effort, data resets). Cloud Run with
  Cloud SQL (about £8-10 a month).
- **Also decided:** The frontend becomes a static SPA build, served by Caddy, as its own backlog task. Approved
  dependencies: SQLAlchemy, Alembic, Caddy (image).

## 2026-11-08 Scope change after reading the course rubric

- **Decision:** MCP server, agent pack and security scan move to Future to-do (not scored). Added observability,
  an alert on user impact and a stretch on-call agent. CI/CD targets 2 of 3 points. Tests cover unit, frontend
  and integration with one command. Each task records its self-check as an issue comment. Timeline starts 8 Nov.
- **Why:** The rubric (12 criteria, 24 points, 10 to pass) scores observability, alerting and the on-call agent
  and does not score MCP or security scanning.
- **Alternatives:** Keep the MCP server as an unscored demo feature. Build a dev/prod split for 3 CI/CD points
  (needs a second VM, not free).

## 2026-11-08 Static SPA build through a separate Vite config

- **Decision:** `npm run build` uses `frontend/vite.spa.config.ts` (TanStack Start in SPA mode, no Nitro, output in
  `dist/client`). The Lovable config stays as `npm run build:lovable`.
- **Why:** The Lovable config always adds Nitro with a Cloudflare target and did not write an `index.html` in SPA
  mode. The plain config produces a prerendered shell that Caddy serves with an index.html fallback.
- **Alternatives:** Run the Nitro Node server as a third container (more memory on the 1 GB VM). Patch the Lovable
  config (fragile, it is regenerated by Lovable).

## 2026-11-08 Observability: Grafana Cloud free tier

- **Decision:** The backend sends OpenTelemetry (OTLP) metrics, traces and logs straight to Grafana Cloud free
  tier, which also hosts the alert rule. Free-tier limits to be confirmed from Grafana's pricing page at the start
  of task 16. OpenTelemetry packages are added only after the user approves them.
- **Why:** One UI links trace, log and metric by trace ID. No collector on the 1 GB VM. Vendor-neutral OTLP, so
  not tied to GCP. Alerts can call a webhook for the on-call agent.
- **Alternatives:** GCP Cloud Logging, Trace and Monitoring (three consoles, GCP-specific, separate alert
  channel).

## 2026-11-08 CI/CD: versioned images in GHCR, dev/prod split kept easy

- **Decision:** CI builds versioned images (tagged with the git SHA) and pushes them to GHCR. The VM pulls a given
  tag. Rollback means redeploying the previous tag. After task 14, measure VM memory and report whether a second
  (dev) stack would fit. Target: 2 of 3 CI/CD points.
- **Why:** The same tag mechanism supports a later dev/prod split with no pipeline redesign.
- **Alternatives:** Build on the VM (slow on an e2-micro, no rollback artefact).

## 2026-11-08 Auth implementation: PyJWT, HS256, demo users created on first login

- **Decision:** Add PyJWT. Tokens are HS256, 8 hours, claims `sub` (demo user name) and `role`. The secret comes
  from `JWT_SECRET`. If unset, a random per-process secret is used and a warning is logged. Demo users
  ("Demo Analyst", "Demo Reviewer") are created in `users` on first login. Role is read from the token.
- **Why:** The user approved JWT. A maintained library avoids hand-written signature checks. Roles are fixed by
  the plan, so no password is needed.
- **Alternatives:** Signing tokens with the standard library (more code to get right). Storing users only via
  the seed (task 10) which would make login depend on seeding.

## 2026-11-08 Draft editing: any signed-in user (gate 2)

- **Decision:** Any signed-in user can edit any Draft scenario, not only its author.
- **Why:** Lets analysts and reviewers refine drafts created by others, and later by the AI assistant. Drafts
  carry no pricing decision until submitted, and every edit is in the audit trail.
- **Alternatives:** Author-only editing (blocks hand-over and AI-created drafts).

## 2026-11-08 Four-eyes rule on approval (gate 2)

- **Decision:** A reviewer cannot approve or reject a scenario they created, edited or submitted (403, with a
  test). Task 9 enforces it from the audit trail. The user specified "edited or submitted". Creating the draft
  is treated as authoring, so it is included. Say if you want creation excluded.
- **Why:** A second person must review what the first person proposed.
- **Alternatives:** Block only the submitter (a reviewer who edited the numbers could still approve them).

## 2026-11-08 QA runs through a subagent, batched

- **Decision:** For tasks in QA scope the engineer spawns the QA subagent without asking. Related QA tasks may
  share one pass. First batch: tasks 7, 8 and 9, after task 9.
- **Why:** Saves round trips and tokens while keeping QA separate from the engineer. See `process.md`.
- **Alternatives:** One QA session per task (more cost, same coverage).

## 2026-11-09 Task 9 criterion amended: moves to Draft have no endpoint

- **Decision:** The criterion "every other transition returns 409" now reads: "Every other transition returns 409.
  Moves to Draft are not possible and have no endpoint (404), with a test for each of the four."
- **Why:** QA round 1 found the four moves into Draft return 404 because no route exists. A route that only
  returns 409 would add API surface for an action that must never happen.
- **Alternatives:** Add a dummy route returning 409 for moves to Draft.

## 2026-11-09: Local stack, mock override and the one test command

- **Decision:** `docker-compose.yml` builds the web image (Node build stage, then Caddy) and the backend, and pulls the
  published pricing image. Only Caddy is published (port 8080). `docker-compose.mock.yml` swaps the pricing service for the
  test mock. `python scripts/test.py` is the one test command (no `make`, which Windows lacks). The web build sets
  `NODE_OPTIONS=--dns-result-order=ipv4first` because the SPA prerender step failed in the container otherwise.
- **Why:** the published image lacks the proposed fields, so the mock override is the only way to walk the whole app until
  task 19. A Python script needs no new dependency and works on Windows and Linux.
- **Alternatives:** a Makefile (not portable to the author's machine). An npm root script (the backend would need a
  wrapper). A Vite dev proxy (does not test the Caddy path).
